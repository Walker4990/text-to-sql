## 1. 배경과 범위

### 1.1 문제

지금은 항목 **값을 꺼내는** 질문(속성 조회)만 된다. 항목 **값으로 거르는** 질문은 안 된다.

> "국내전용연회비가 30000원 이하인 카드 목록 알려줘"

| 문제 | 내용 |
|---|---|
| 조건이 조용히 빠짐 [현행] | 모델이 계층 조회로 분류하면 조건 없는 전체 목록 SQL이 정상처럼 나온다 |
| 기준일자도 일부만 적용 [현행] | `base_date`는 단건·목록에만 들어가고 구조·속성·계층 조회에서는 SQL에 반영되지 않는다 (스키마는 받는데 빌더가 무시) |
| 속성 컬럼이 문자열 | 항목은 `CHAR01` 같은 문자열 컬럼이라 그대로 비교하면 `'100000' < '30000'`이 된다 |

### 1.2 범위 (2026-11-12 사용자 확정)

| 포함 | 내용 |
|---|---|
| 숫자 비교 | `=`, `<>`, `<`, `<=`, `>`, `>=` |
| 문자 조건 | 같음, 다름, 포함 (`LIKE`) |
| 기준일자 확장 | 구조·속성·계층 조회에도 `:base_dt BETWEEN VF_DT AND VT_DT` 적용 |
| 항목 사전 형식 | 항목마다 `text`/`number` 형식. 시트 `항목` 탭에 `형식` 열 추가 |
| 안전장치 | 조건을 해석하지 못하면 조건 없는 SQL을 내지 않고 거절한다 |

| 제외 | 이유 |
|---|---|
| OR 조건, 괄호 | 조건은 모두 AND로만 묶는다 |
| 단위 환산 ("3만원", "5천") | 질문에 적힌 숫자 그대로만 쓴다. 환산 값은 질문에 없는 값이라 거절한다 (6.2) |
| 다중값 항목 조건 | 값이 `OBJ_DETAIL_REL` 경유라 단순 조건으로 안 된다 [현행 거절 유지] |
| 날짜 항목 비교 | 날짜 항목은 `text`로 두고 같음·포함만 쓴다 |

## 2. 지원하는 질문 [신규]

| 질문 | kind | 조건 |
|---|---|---|
| "국내전용연회비가 30000 이하인 카드상품 목록" | hierarchy (카드상품 → 연회비) | 연회비 단계의 국내전용연회비 ≤ 30000 |
| "가입최저나이가 30 이하인 보험상품 목록" | list | 보험상품 자신의 항목 |
| "INS001 보험상품과 연결된 특약 중 특약보험료가 10000 초과인 것" | hierarchy | 특약 단계 조건 |
| "ETF 중 총보수가 0.5 이하인 것의 기초지수 알려줘" | attribute | 같은 유형의 항목 조건 + 값 꺼내기 |
| "운용사에 한화가 들어간 펀드 목록" | list | 문자 포함 조건 |
| "2026년 11월 12일 기준 CRD001 카드의 하위 구조" | structure | 기준일자 (조건 아님) |

조건은 최대 5개이며 모두 AND다. 조건이 걸린 항목 값은 결과 열에도 함께 나온다 (사용자가 값을 눈으로 확인할 수 있게).

## 3. 의도(Intent) 변경 [신규]

```python
class Condition(BaseModel):
    item: str    # 항목 이름 (형식 [가-힣A-Za-z0-9_]{1,30})
    op: Literal["eq", "ne", "lt", "le", "gt", "ge", "contains"]
    value: str   # 최대 50자. 숫자 항목이면 빌더가 숫자 형식을 검사한다

class Intent:
    conditions: list[Condition] | None = Field(default=None, max_length=5)
```

- `type`(어느 유형의 항목인지)은 의도에 넣지 않는다. 7b 모델이 챙길 칸을 줄이기 위해 **빌더가 항목 이름으로 단계를 찾는다** (5.4).
- 연산자 이름은 SQL 기호가 아니라 영문 이름이다. 기호를 LLM이 쓰게 하지 않고, 허용 목록 밖은 스키마에서 막힌다.
- **종류별 규칙**: `conditions`는 `list`, `attribute`, `hierarchy`에서만 쓴다. 다른 종류에 값이 있으면 검증 오류다.
- **hierarchy 필수값 완화**: 지금은 `target_type`, `code 또는 code_item`, `path`가 필수다. "카드 목록 + 연회비 조건"에는 코드가 없으므로 `code`, `code_item`, `conditions` 중 **하나 이상**이 있으면 된다. 코드도 조건도 없는 계층 전체 덤프는 지금처럼 거절한다.
- `hierarchy`에도 `base_date`를 허용한다 (스키마 갈래에 칸 추가).

## 4. 항목 형식 (type) [신규]

### 4.1 항목 사전

```json
"연회비": {
  "국내전용연회비": { "column": "CHAR01", "type": "number" },
  "비고": { "column": "TEXT01" }
}
```

- `type`은 `"text"`(기본) 또는 `"number"`. 다른 값은 `MetadataError`다.
- `ItemDef(column, multi=False, type="text")`. 기존 파일은 `type`이 없으므로 모두 `text`로 읽힌다.
- **형식이 text인 항목에 대소 비교(`lt`, `le`, `gt`, `ge`)를 하면 거절**한다. 문자열 비교로 조용히 틀리는 것보다 낫다. 반대로 number 항목에 `contains`도 거절한다.

| 형식 | 허용 연산자 |
|---|---|
| number | eq, ne, lt, le, gt, ge |
| text | eq, ne, contains |

### 4.2 시트 `항목` 탭

| 유형명 | 항목명 | 물리컬럼 | 다중값 | **형식** | 사용 | 설명 |
|---|---|---|---|---|---|---|
| 연회비 | 국내전용연회비 | CHAR01 | N | 숫자 | Y | |

- `형식` 열은 선택이다. 없거나 빈 칸이면 `text`. 값은 `숫자`/`number`, `문자`/`text` (대소문자 무시). 그 밖의 값은 MV-05 오류다.
- 동기화 도구의 차이 보고: 형식 변경은 **위험** 변경이다 (같은 질문의 SQL이 달라진다).
- CSV 내보내기는 `숫자`/`문자`로 쓴다.

## 5. SQL 생성 [신규]

### 5.1 연산자

| op | number 항목 | text 항목 |
|---|---|---|
| eq | `= :cond_n` | `= :cond_n` |
| ne | `<> :cond_n` | `<> :cond_n` |
| lt, le, gt, ge | `<`, `<=`, `>`, `>=` | 거절 |
| contains | 거절 | `LIKE :cond_n ESCAPE '\'` (값은 `%값%`, `% _ \`는 이스케이프) |

### 5.2 숫자 비교 식

속성 컬럼이 문자열이므로 숫자일 때만 변환한다. 숫자가 아닌 값(빈 칸, 문자)이 있어도 **오류 없이 비교에서 빠지도록** 정규식으로 먼저 거른다.

| 방언 | 컬럼 식 (`{c}` = `D.CHAR01`) |
|---|---|
| postgresql | `CASE WHEN {c} ~ '^-?[0-9]+(\.[0-9]+)?$' THEN CAST({c} AS NUMERIC) END` |
| oracle | `CASE WHEN REGEXP_LIKE({c}, '^-?[0-9]+(\.[0-9]+)?$') THEN TO_NUMBER({c}) END` |

- 방언은 `common.json`의 `dialect` (기본 postgresql). 다른 값이면 숫자 조건에서 `UnsupportedQuestionError`.
- 값이 문자열이어서 변환할 수 없는 행은 `NULL`이 되어 조건이 거짓이다. 값은 공백 없는 숫자 문자열이라고 가정한다 (한계, 7장).

### 5.3 값 바인딩

- 값은 항상 바인드 변수 `:cond_0`, `:cond_1`, ... (조건 순서). SQL 문자열에 직접 넣지 않는다.
- **숫자 값 형식**: `^-?\d{1,15}(\.\d{1,6})?$`. 아니면 `UnsupportedQuestionError`.
  - 정수면 `int`로 바인딩 (`<= 30000`).
  - 소수면 문자열로 바인딩하고 SQL에서 변환한다 (`<= CAST(:cond_0 AS NUMERIC)`, Oracle은 `TO_NUMBER(:cond_0)`). 챗봇의 응답 모델이 `str | int`만 받으므로 `float`는 쓰지 않는다.
- 문자 값은 문자열로 바인딩한다.

### 5.4 조건이 걸리는 곳

| kind | 조건 항목의 출처 | SQL |
|---|---|---|
| list | `target_type`의 항목 | `OBJ_DETAIL D`를 조인 (`D.KIND = :detail_kind`, 최신 버전). 열: `SID, BIZCODE, OBJ_NAME` + 조건 항목 |
| attribute | `target_type`의 항목 | 기존 조인에 조건 추가. 조건 항목이 `attributes`에 없으면 열에 덧붙인다 |
| hierarchy | 경로 유형(`target_type` + `path`)의 항목 | 항목 이름이 **정확히 한 유형**에만 있으면 그 단계의 `OBJ_DETAIL`(`D{n}`)에 건다. 없으면 "경로에 없는 항목", 둘 이상이면 "여러 유형에 있는 항목" 거절 |

- 같은 유형의 조건은 한 번의 조인을 공유한다 (같은 `KIND = 1` 행).
- 계층 조회에서 조건이 걸린 단계는 `D{n}` 조인이 없으면 만들고, 조건 항목을 결과 열에 포함한다.
- 항목이 `multi`면 [현행]처럼 거절한다.

### 5.5 기준일자 확장

`base_date`가 있으면 **쿼리에 나오는 모든 `OBJ_MAIN` 별칭**에 `:base_dt BETWEEN X.VF_DT AND X.VT_DT`를 붙인다 (단건·목록과 같은 규칙).

| kind | 적용 별칭 |
|---|---|
| structure | 상위 `P`, 하위 `C` |
| attribute | `M` |
| hierarchy | 모든 단계 `L0`..`Ln` |

- **VF_DT/VT_DT의 의미는 아직 미확정이다** (요구사항 정의서 6.3 1번). `OBJ_INV`·`OBJ_DETAIL`에는 걸지 않는다. 의미가 확정되면 범위를 다시 정한다.

## 6. 추출기 [신규]

### 6.1 스키마·프롬프트

- 스키마: `conditions` 배열 (`item`은 항목 이름 enum, `op`는 연산자 enum, `value`는 문자열). `list`, `attribute`, `hierarchy` 갈래에만 칸이 있다. 항목이 없는 프로필이면 만들지 않는다.
- 프롬프트의 `[항목]` 목록에서 숫자 항목에 `(숫자)`를 붙여 모델이 구분하게 한다 (예: `연회비: 국내전용연회비(숫자), 비고`).
- 규칙: 이하=`le`, 이상=`ge`, 미만=`lt`, 초과=`gt`, 같은·인=`eq`, 아닌=`ne`, 포함·들어간=`contains`. 값은 질문에 적힌 숫자 그대로 쓴다 (쉼표·단위 없이 숫자만).
- 예시는 프로필의 숫자 항목·문자 항목으로 만든다 (프로필에 없는 이름을 예시로 보이지 않기 위해, [현행] 예시 생성 방식과 같다).

### 6.2 근거 확인 (코드가 한다)

모델이 지어낸 조건이 SQL에 들어가지 않도록, 의도를 받은 뒤 코드로 검사한다.

| 검사 | 실패하면 |
|---|---|
| 조건의 항목 이름이 질문(공백 제거)에 그대로 있다 | 거절: "조건의 항목이나 값이 질문에 없습니다" |
| 조건의 값이 질문에 있다 (숫자 값은 질문과 값의 쉼표를 지우고 비교) | 같음 |

"3만원 이하"를 모델이 `30000`으로 바꿔도 질문에 `30000`이 없으므로 거절된다. 환산을 허용하지 않는 이유다.

### 6.2.1 하위 유형 항목 조건 보정 (코드가 한다)

"국내전용연회비가 30000 이하인 카드상품 목록"에서 `국내전용연회비`는 카드상품이 아니라 하위 유형 `연회비`의 항목이다.
7b 모델은 이런 질문을 `list`(대상 카드상품)로 답하는 일이 잦고, 그대로 두면 "카드상품에 없는 항목"으로 거절된다.
그래서 의도를 받은 뒤 코드(`_reroute_child_conditions`)가 아래 조건을 모두 만족할 때만 `hierarchy`로 바꾼다.

| 조건 | 만족하지 않으면 |
|---|---|
| 종류가 `list`이고 `conditions`·`target_type`이 있다 | 그대로 둔다 |
| 대상 유형에 없는 조건 항목이 하나 이상 있다 | 그대로 둔다 (자기 항목이면 보정할 필요 없음) |
| 그 항목들이 모두 **다른 한 유형**에만 있다 | 그대로 둔다 → 빌더가 거절 (어느 유형인지 추측하지 않는다) |

바꾼 결과: `kind="hierarchy"`, `path=[그 유형]` (예: `path=["연회비"]`). 대상과 그 유형 사이에 실제 구조가 없으면 결과가 0건일 뿐 SQL은 안전하다.
`attribute`는 보정하지 않는다. 무엇을 꺼낼지가 달라져 추측할 수 없기 때문이다.
테스트: `tests/test_condition_extractor.py` 문제 15-1~15-3.

### 6.3 가드 (조건을 해석 못 했을 때)

질문에 비교 표현이 있는데 의도에 `conditions`가 없으면, 조건이 빠진 SQL이 나오지 않도록 거절한다.

- 표현: `이하`, `이상`, `초과`, `미만`, `넘는`, `넘게`, `보다 큰`, `보다 작`, `보다 많`, `보다 적` (공백 유무 모두)
- 사유: "값 조건을 해석하지 못했습니다. '항목이름 + 값 + 이하/이상' 형태로 질문해 주세요"
- 비교 표현이 없는 문장에는 영향이 없다. 일반 질문의 거짓 거절은 표현 목록을 보수적으로 두어 줄인다.

## 7. 한계

| 한계 | 내용 |
|---|---|
| 값 형식 | 숫자 항목의 값이 공백 없는 숫자 문자열이라고 가정한다. `1,000`, `30%`, `3년`처럼 기호·단위가 섞인 값은 NULL이 되어 비교에서 빠진다 |
| 단위 | "3만원", "5천"은 환산하지 않고 거절한다 |
| 논리 | AND만. "A 이하 또는 B 이상"은 지원하지 않는다 |
| 날짜 항목 | text로 두고 같음·포함만 쓴다 |
| 항목 이름 | 항목 이름은 질문에 그대로 써야 한다 (별칭 없음) |
| 기준일자 | VF_DT/VT_DT 의미가 확정되지 않아 `OBJ_MAIN`에만 건다 |
| 7b 모델 정확도 | 조건 질문의 분류 정확도는 평가 세트로 재야 한다 (8장) |
