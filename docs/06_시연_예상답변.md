# 시연 예상 답변

챗봇(https://side-chatbot.onrender.com)의 SQL 모드에서 시연용 질문을 했을 때 나올 답변을 정리한 문서다.

- **기준**: text-to-sql main, 시연 프로필 `demo` (기본값)
- **만든 방법**: 실제 빌더·검증기 코드로 생성했다. 질문 → 의도(JSON) 단계는 LLM이 이렇게 뽑을 것으로 **가정**한 값을 넣었다.
- **주의**: LLM 판단에 따라 실제 화면은 달라질 수 있다. 차이가 나면 질문한 시각으로 Render 로그를 찾는다 (5절). requestId는 화면에 보이지 않고 로그와 질문 이력(DB)에만 남는다.

---

## 1. 시연 전 준비

| 순서 | 할 일 | 이유 |
|---|---|---|
| 1 | 시연 10분 전에 사이트에 한 번 접속한다 | Render 무료 플랜은 잠들어 있으면 첫 응답에 40~50초 걸린다 |
| 2 | Supabase 대시보드에서 프로젝트가 Active인지 본다 | 무료 프로젝트는 일주일가량 안 쓰면 일시정지되고, 그러면 서버가 시작하지 못한다 |
| 3 | 로그인 → 질문창 위 토글을 **SQL**로 바꾼다 | 문서 모드에서 물으면 문서 RAG 답변이 나온다 |

## 2. 시연 프로필 (가상 값)

실제 현장 값과 무관한 시연용 유형이다. TYPEID 앞자리가 업권을 나타낸다.

| 업권 | 유형 (TYPEID) | 현장 별칭 |
|---|---|---|
| 보험 (1xxx) | 보험상품(1100), 주계약(1110), 특약(1120), 보장(1130), 보험료율(1140) | 보험, 주보험, 라이더·선택특약, 담보, 요율 |
| 카드 (2xxx) | 카드상품(2100), 카드혜택(2110), 연회비(2120), 제휴가맹점(2130) | 카드, 부가서비스·혜택, 가맹점·제휴사 |
| 증권 (3xxx) | 펀드(3100), ETF(3110), 계좌상품(3120), 거래수수료(3130) | 상장지수펀드, 계좌, 수수료·매매수수료 |

속성 질문(3.7~3.9)에 쓰는 항목 사전이다. **13개 유형 모두** 항목이 있어서 어느 유형이든 속성을 물어볼 수 있다. 항목 값은 OBJ_DETAIL의 해당 컬럼에 들어 있다. 사전에 없는 항목은 조회하지 않는다.

| 유형 | 항목 (OBJ_DETAIL 컬럼) | 다중값 (미지원) |
|---|---|---|
| 보험상품 | 보험기간(CHAR01), 납입기간(CHAR02), 가입최저나이(CHAR03), 가입최고나이(CHAR04) | 판매채널(CHAR05) |
| 주계약 | 보험가입금액(CHAR01), 보험료(CHAR02), 납입주기(CHAR03) | - |
| 특약 | 보장기간(CHAR01), 갱신여부(CHAR02), 특약보험료(CHAR03) | - |
| 보장 | 보장금액(CHAR01), 면책기간(CHAR02), 지급사유(TEXT01) | - |
| 보험료율 | 적용요율(CHAR01), 연령구간(CHAR02), 적용시작일(CHAR03) | - |
| 카드상품 | 카드등급(CHAR01), 브랜드(CHAR02), 발급대상(CHAR03), 전월실적기준(CHAR05) | 제휴브랜드(CHAR04) |
| 카드혜택 | 혜택유형(CHAR01), 할인율(CHAR02), 월한도(CHAR03), 혜택상세(TEXT01) | - |
| 연회비 | 국내전용연회비(CHAR01), 해외겸용연회비(CHAR02), 가족카드연회비(CHAR03) | - |
| 제휴가맹점 | 가맹점업종(CHAR01), 제휴할인율(CHAR02), 가맹점주소(TEXT01) | - |
| 펀드 | 위험등급(CHAR01), 운용사(CHAR02), 환매수수료율(CHAR03), 설정일(CHAR05), 기준가(CHAR06), 투자설명(TEXT01) | 투자지역(CHAR04) |
| ETF | 기초지수(CHAR01), 총보수(CHAR02), 상장시장(CHAR03), 추적배수(CHAR04) | - |
| 계좌상품 | 계좌유형(CHAR01), 최소가입금액(CHAR02), 이자율(CHAR03) | 가입채널(CHAR04) |
| 거래수수료 | 수수료율(CHAR01), 최소수수료(CHAR02), 적용시장(CHAR03) | - |

룰 변수 질문(3.10~3.12)에 쓰는 **등록 항목명칭**이다. 금융권 현장의 메타데이터를 솔루션 항목관리에 등록했다고 가정한 샘플이다. 질문에 이 이름을 말하면 BIZCODE 조건이 PF 룰 문법(`<$@[항목명칭]@$>`)으로 나온다.

| 등록 항목명칭 (가상) |
|---|
| 상품코드, 수수료코드, 카드상품코드, 특약코드, 펀드코드, 주계약코드, 보장코드, 요율코드, 카드혜택코드, 가맹점코드, ETF코드, 계좌상품코드 |

## 3. 질문별 예상 답변

한눈에 보기:

| # | 질문 | 종류 | 결과 |
|---|---|---|---|
| 3.1 | 라이더 목록 보여줘 | 목록 | SQL (TYPEID 1120) |
| 3.2 | INS001 보험상품 알려줘 | 단건 | SQL (TYPEID 1100) |
| 3.3 | CRD001 카드에 연결된 하위 오브젝트 | 하위 구조 | SQL (TYPEID 2100) |
| 3.4 | 글로벌 들어간 펀드 찾아줘 | 이름 검색 | SQL (TYPEID 3100) |
| 3.5 | FEE01 수수료가 붙은 상위 상품 | 상위 구조 | SQL (TYPEID 3130) |
| 3.6 | 오늘 날씨 어때 | 거절 | "상품 DB 질문이 아님" |
| 3.7 | INS001 보험상품의 보험기간이랑 납입기간 알려줘 | 속성 | SQL (TYPEID 1100, OBJ_DETAIL) |
| 3.8 | 글로벌 들어간 펀드의 위험등급, 운용사 알려줘 | 속성 + 이름 검색 | SQL (TYPEID 3100, OBJ_DETAIL) |
| 3.9 | INS001 보험상품의 판매채널 알려줘 | 거절 | "다중값 항목은 아직 지원하지 않습니다: 판매채널" |
| 3.10 | FEE01 수수료가 붙은 상위 상품, 수수료코드 항목으로 | 룰 변수 (기본 IN 조건) | `C.BIZCODE IN (<$@distinct([수수료코드].array)@$>)` |
| 3.11 | 상품코드 여러 개로 보험상품의 보험기간 알려줘 | 룰 변수 (IN 조건) + 속성 | `M.BIZCODE IN (<$@distinct([상품코드].array)@$>)` |
| 3.12 | 질병코드 항목으로 보험상품 알려줘 | 거절 | "등록되지 않은 항목입니다: 질병코드" |
| 3.13 | 보험상품코드를 다중값으로 받고, 주계약 특약 보장 구조의 속성값들을 출력 | 여러 단계 계층 + 속성 | 보험상품 → 주계약 → 특약 → 보장, 단계별 OBJ_DETAIL |

### 3.1 라이더 목록 보여줘

- **보여 줄 점**: 현장 별칭(라이더)을 정식 유형(특약)으로 바꿔 조회한다.
- **예상 의도**: `{"kind": "list", "target_type": "특약"}` ("라이더"로 뽑아도 결과는 같다)
- **params**: `{"type_id": 1120}`

```sql
SELECT M.SID, M.BIZCODE, M.OBJ_NAME
FROM OBJ_MAIN M
WHERE M.TYPEID = 1120 AND M.END_DT = '99991231'
ORDER BY M.BIZCODE
```

### 3.2 INS001 보험상품 알려줘

- **보여 줄 점**: 코드로 한 건을 찾는다. 현재 버전(`END_DT = '99991231'`)만 조회한다.
- **예상 의도**: `{"kind": "lookup", "target_type": "보험상품", "code": "INS001"}`
- **params**: `{"type_id": 1100, "code": "INS001"}`

```sql
SELECT M.SID, M.BIZCODE, M.OBJ_NAME
FROM OBJ_MAIN M
WHERE M.TYPEID = 1100 AND M.BIZCODE = 'INS001' AND M.END_DT = '99991231'
```

### 3.3 CRD001 카드에 연결된 하위 오브젝트

- **보여 줄 점**: 구조 테이블(OBJ_INV)을 JOIN해 카드상품 아래에 연결된 오브젝트를 찾는다.
- **예상 의도**: `{"kind": "structure", "target_type": "카드상품", "code": "CRD001", "direction": "children"}`
- **params**: `{"type_id": 2100, "code": "CRD001"}`

```sql
SELECT C.SID, C.BIZCODE, C.OBJ_NAME
FROM OBJ_MAIN P
JOIN OBJ_INV I ON I.SID = P.SID
JOIN OBJ_MAIN C ON C.SID = I.SUBSID
WHERE P.TYPEID = 2100 AND P.BIZCODE = 'CRD001'
  AND P.END_DT = '99991231' AND I.END_DT = '99991231' AND C.END_DT = '99991231'
ORDER BY C.BIZCODE
```

> ⚠️ "CRD001 카드에 연결된 **부가서비스**"로 묻지 않는다. 구조 조회는 하위 유형으로 거르지 않으므로 부가서비스뿐 아니라 연회비·제휴가맹점 등 모든 하위가 나와 질문과 어긋난다. LLM이 "부가서비스"를 대상 유형으로 잘못 골라 `TYPEID = 2110`이 나올 수도 있다.

### 3.4 글로벌 들어간 펀드 찾아줘

- **보여 줄 점**: 이름 일부로 검색한다. 검색어 안의 `%`, `_`는 글자 그대로 찾도록 이스케이프한다.
- **예상 의도**: `{"kind": "lookup", "target_type": "펀드", "name_keyword": "글로벌"}`
- **params**: `{"type_id": 3100, "name_keyword": "%글로벌%"}`

```sql
SELECT M.SID, M.BIZCODE, M.OBJ_NAME
FROM OBJ_MAIN M
WHERE M.TYPEID = 3100 AND M.OBJ_NAME LIKE '%글로벌%' ESCAPE '\' AND M.END_DT = '99991231'
```

### 3.5 FEE01 수수료가 붙은 상위 상품

- **보여 줄 점**: 3.3과 반대 방향(하위 → 상위)으로 찾는다. 별칭 "수수료"를 거래수수료로 바꾼다.
- **예상 의도**: `{"kind": "structure", "target_type": "거래수수료", "code": "FEE01", "direction": "parents"}`
- **params**: `{"type_id": 3130, "code": "FEE01"}`

```sql
SELECT P.SID, P.BIZCODE, P.OBJ_NAME
FROM OBJ_MAIN P
JOIN OBJ_INV I ON I.SID = P.SID
JOIN OBJ_MAIN C ON C.SID = I.SUBSID
WHERE C.TYPEID = 3130 AND C.BIZCODE = 'FEE01'
  AND P.END_DT = '99991231' AND I.END_DT = '99991231' AND C.END_DT = '99991231'
ORDER BY P.BIZCODE
```

### 3.6 오늘 날씨 어때

- **보여 줄 점**: 상품 DB와 관계없는 질문에는 SQL을 만들지 않고 사유를 답한다.
- **예상 답변**: 지원하지 않음 - "상품 DB 질문이 아님" (문구는 LLM이 정하므로 조금 다를 수 있다)
- 관리자 이력에 미답변으로 저장된다.

### 3.7 INS001 보험상품의 보험기간이랑 납입기간 알려줘

- **보여 줄 점**: 속성 테이블(OBJ_DETAIL)을 JOIN해 항목 값을 조회한다. 항목 이름이 컬럼(CHAR01, CHAR02)으로 바뀌고, 결과 열 이름은 한글 항목명으로 붙는다. `D.KIND = 1`은 오브젝트의 기본 속성 행이다.
- **예상 의도**: `{"kind": "attribute", "target_type": "보험상품", "code": "INS001", "attributes": ["보험기간", "납입기간"]}`
- **params**: `{"type_id": 1100, "code": "INS001", "detail_kind": 1}`

```sql
SELECT M.BIZCODE, M.OBJ_NAME, D.CHAR01 "보험기간", D.CHAR02 "납입기간"
FROM OBJ_MAIN M
JOIN OBJ_DETAIL D ON D.SID = M.SID
WHERE M.TYPEID = 1100 AND M.BIZCODE = 'INS001' AND D.KIND = 1
  AND M.END_DT = '99991231' AND D.END_DT = '99991231'
ORDER BY M.BIZCODE
```

### 3.8 글로벌 들어간 펀드의 위험등급, 운용사 알려줘

- **보여 줄 점**: 코드 대신 이름 일부로도 속성을 조회한다. 이름이 겹치는 펀드가 여러 개면 펀드마다 한 줄씩 나온다.
- **예상 의도**: `{"kind": "attribute", "target_type": "펀드", "name_keyword": "글로벌", "attributes": ["위험등급", "운용사"]}`
- **params**: `{"type_id": 3100, "name_keyword": "%글로벌%", "detail_kind": 1}`

```sql
SELECT M.BIZCODE, M.OBJ_NAME, D.CHAR01 "위험등급", D.CHAR02 "운용사"
FROM OBJ_MAIN M
JOIN OBJ_DETAIL D ON D.SID = M.SID
WHERE M.TYPEID = 3100 AND M.OBJ_NAME LIKE '%글로벌%' ESCAPE '\' AND D.KIND = 1
  AND M.END_DT = '99991231' AND D.END_DT = '99991231'
ORDER BY M.BIZCODE
```

### 3.9 INS001 보험상품의 판매채널 알려줘

- **보여 줄 점**: 값이 여러 개 들어가는 항목(다중값)은 아직 템플릿이 없어서, 틀린 SQL을 만들지 않고 거절한다.
- **예상 답변**: 지원하지 않음 - "다중값 항목은 아직 지원하지 않습니다: 판매채널"
- 사전에 없는 항목도 같은 방식으로 거절한다. 예: "CRD001 카드의 적립률" → "'카드상품' 유형에 '적립률' 항목이 없습니다"
- LLM이 이런 질문을 `unsupported`로 판단하면 LLM이 쓴 사유가 대신 나온다. 어느 쪽이든 SQL은 나오지 않는다.

### 3.10 FEE01 수수료가 붙은 상위 상품, 수수료코드 항목으로

- **보여 줄 점**: 3.5와 같은 질문인데 끝에 항목명칭을 말했다. BIZCODE 조건에 값(`'FEE01'`) 대신 PF 룰 문법이 들어가서, 룰에 그대로 붙여 쓸 수 있다. 실행할 때 룰 엔진이 값을 넣는다.
- **예상 의도**: `{"kind": "structure", "target_type": "거래수수료", "code": "FEE01", "code_item": "수수료코드", "direction": "parents"}`
- **params**: `{"type_id": 3130}` (code가 빠진다)
- DB 룰에서 BIZCODE는 보통 여러 값으로 받으므로 기본이 IN 조건이다. "수수료코드 하나로"처럼 값이 하나라고 말하면 `C.BIZCODE = <$@[수수료코드]@$>`가 된다.

```sql
SELECT P.SID, P.BIZCODE, P.OBJ_NAME
FROM OBJ_MAIN P
JOIN OBJ_INV I ON I.SID = P.SID
JOIN OBJ_MAIN C ON C.SID = I.SUBSID
WHERE C.TYPEID = 3130 AND C.BIZCODE IN (<$@distinct([수수료코드].array)@$>)
  AND P.END_DT = '99991231' AND I.END_DT = '99991231' AND C.END_DT = '99991231'
ORDER BY P.BIZCODE
```

> 룰 변수는 질문에서 지목한 오브젝트(여기서는 하위 쪽 C)의 BIZCODE 한 곳에만 들어간다. 결과 쪽이나 다른 컬럼에 거는 조건은 사람이 마지막에 손본다.

### 3.11 상품코드 여러 개로 보험상품의 보험기간 알려줘

- **보여 줄 점**: "여러 개", "목록", "배열"처럼 값이 여러 개라고 말하면 `IN (<$@distinct([…].array)@$>)` 형식이 된다. 코드 값 없이 항목명칭만으로도 질문할 수 있다.
- **예상 의도**: `{"kind": "attribute", "target_type": "보험상품", "code_item": "상품코드", "code_item_multi": true, "attributes": ["보험기간"]}`
- **params**: `{"type_id": 1100, "detail_kind": 1}`

```sql
SELECT M.BIZCODE, M.OBJ_NAME, D.CHAR01 "보험기간"
FROM OBJ_MAIN M
JOIN OBJ_DETAIL D ON D.SID = M.SID
WHERE M.TYPEID = 1100 AND M.BIZCODE IN (<$@distinct([상품코드].array)@$>) AND D.KIND = 1
  AND M.END_DT = '99991231' AND D.END_DT = '99991231'
ORDER BY M.BIZCODE
```

### 3.12 질병코드 항목으로 보험상품 알려줘

- **보여 줄 점**: 항목관리에 등록되지 않은 이름은 SQL을 만들지 않는다. 오타나 없는 항목이 룰에 들어가는 것을 막는다.
- **예상 답변**: 지원하지 않음 - "등록되지 않은 항목입니다: 질병코드"
- LLM이 질문에 없는 항목명칭을 스스로 지어내면 "질문을 이해하지 못했습니다"로 거절된다. 항목명칭은 질문에 직접 말한 것만 쓴다.

### 3.13 보험상품코드를 다중값으로 받고, 주계약 특약 보장 구조의 속성값들을 출력

- **보여 줄 점**: 여러 단계 계층을 한 번에 내려간다(최대 4단계). 단계마다 유형(TYPEID)으로 걸러서 주계약·특약·보장만 나오고, 각 단계의 속성은 OBJ_DETAIL을 LEFT JOIN 해서 붙인다(값이 없어도 구조 행은 나온다).
- 항목을 말하지 않으면 경로 각 유형의 단일값 항목을 전부 출력한다. "주계약의 보험료, 보장의 보장금액만"처럼 말하면 그 항목만 나온다.
- "INS001 보험상품과 연결된 주계약 목록"처럼 한 단계만 말해도 hierarchy로 처리되어 **하위 중 주계약만** 나온다(3.3의 하위 구조는 유형으로 거르지 않는다).
- **예상 의도**: `{"kind": "hierarchy", "target_type": "보험상품", "code_item": "상품코드", "path": ["주계약", "특약", "보장"]}`
- **params**: `{"type_id": 1100, "type_id_1": 1110, "detail_kind": 1, "type_id_2": 1120, "type_id_3": 1130}`

```sql
SELECT L0.BIZCODE "보험상품", L0.OBJ_NAME "보험상품명",
       L1.BIZCODE "주계약", L1.OBJ_NAME "주계약명", D1.CHAR01 "보험가입금액", D1.CHAR02 "보험료", D1.CHAR03 "납입주기",
       L2.BIZCODE "특약", L2.OBJ_NAME "특약명", D2.CHAR01 "보장기간", D2.CHAR02 "갱신여부", D2.CHAR03 "특약보험료",
       L3.BIZCODE "보장", L3.OBJ_NAME "보장명", D3.CHAR01 "보장금액", D3.TEXT01 "지급사유", D3.CHAR02 "면책기간"
FROM OBJ_MAIN L0
JOIN OBJ_INV I1 ON I1.SID = L0.SID JOIN OBJ_MAIN L1 ON L1.SID = I1.SUBSID AND L1.TYPEID = 1110
LEFT JOIN OBJ_DETAIL D1 ON D1.SID = L1.SID AND D1.KIND = 1 AND D1.END_DT = '99991231'
JOIN OBJ_INV I2 ON I2.SID = L1.SID JOIN OBJ_MAIN L2 ON L2.SID = I2.SUBSID AND L2.TYPEID = 1120
LEFT JOIN OBJ_DETAIL D2 ON D2.SID = L2.SID AND D2.KIND = 1 AND D2.END_DT = '99991231'
JOIN OBJ_INV I3 ON I3.SID = L2.SID JOIN OBJ_MAIN L3 ON L3.SID = I3.SUBSID AND L3.TYPEID = 1130
LEFT JOIN OBJ_DETAIL D3 ON D3.SID = L3.SID AND D3.KIND = 1 AND D3.END_DT = '99991231'
WHERE L0.TYPEID = 1100 AND L0.BIZCODE IN (<$@distinct([상품코드].array)@$>)
  AND L0.END_DT = '99991231'
  AND I1.END_DT = '99991231' AND L1.END_DT = '99991231'
  AND I2.END_DT = '99991231' AND L2.END_DT = '99991231'
  AND I3.END_DT = '99991231' AND L3.END_DT = '99991231'
ORDER BY L0.BIZCODE, L1.BIZCODE, L2.BIZCODE, L3.BIZCODE
```

## 5. 결과가 예상과 다를 때

| 증상 | 확인할 곳 |
|---|---|
| 첫 질문이 오래 걸리거나 타임아웃 | 서버가 깨어나는 중. 1분 뒤 다시 시도. 계속되면 Render 대시보드 → Logs |
| 항목명칭을 말했는데 값(`= 'FEE01'`)이 나옴 | LLM이 항목명칭을 못 뽑았다. "수수료코드 항목으로"처럼 2절 등록 목록의 이름을 그대로 넣어 다시 묻는다 |
| 속성 질문인데 "항목이 없습니다" | LLM이 항목 이름을 사전과 다르게 뽑았을 수 있다(예: "보험 기간"). 2절 항목 표의 이름 그대로 다시 묻는다 |
| 정상 질문인데 "지원하지 않음" | LLM이 유형을 잘못 골랐을 수 있다. 질문한 시각 근처의 Render 로그에서 `SQL 모드 거절 requestId=... reason=...` 줄을 찾는다 |
| "LLM 서버에 연결할 수 없습니다" (502) | OpenAI 키 만료·크레딧 부족. Render → Environment의 `OPENAI_API_KEY` 확인 |
| "SQL 모드를 지금 사용할 수 없습니다" (503) | 서버 시작 때 SQL 서비스 준비 실패. Render 로그의 `SQL 모드를 시작하지 못했습니다` 줄 확인 |
| 이력 확인 | 관리자 화면 → 질문 이력 (모드 열이 `sql`인 행) |
