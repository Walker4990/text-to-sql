# Text-to-SQL PoC 기능 명세서

작성일: 2026-11-02 / 요구사항 ID는 `01_요구사항정의서.md` 기준

## 1. 전체 구조

```
질문(자연어)
  → [의도 추출기] LLM이 JSON 의도만 추출 (SQL은 쓰지 않음)
  → [Intent 검증] 형식·필수값 검증
  → [SQL 빌더]   메타데이터 + 템플릿으로 SQL 조립
  → [SQL 검증기] SELECT만, 허용 테이블만
  → 응답(SQL, 바인드 값, 의도, requestId)
```

레이어: Controller(FastAPI) → Service → Repository(메타데이터). 의존성은 생성자 주입.

## 2. 대상 테이블 (PF ERD, InnoProduct 자료 기준)

**OBJ_MAIN** (오브젝트 메인): SID(키), BIZCODE(오브젝트 코드), TYPEID(OBJ1000 유형), OBJ_NAME, OBJ_DESC, DISP_ORDER, VF_DT/VT_DT(적용 시작·종료일), END_DT(버전 종료일, `99991231` = 최신 버전)

**OBJ_INV** (오브젝트 구조): INV_TYPE(1 기본, 2 서비스뷰), SID(상위 → OBJ_MAIN.SID), SUBSID(하위 → OBJ_MAIN.SID), SEQ, VF_DT/VT_DT, DISP_SEQ, END_DT, PROP_SID

**OBJ_DETAIL** (오브젝트 속성): SID(→ OBJ_MAIN), KIND(1 오브젝트 기본 속성 / 그 외 패턴 TYPEID), SEQ(일련번호, 패턴 행 구분), VF_DT/VT_DT, END_DT, DESC01~02(긴 문자열), CHAR01~300(일반 값), TEXT01~40(중간 길이 값)

**패턴 관련 정의 테이블**
- OBJ1000(유형): 패턴도 유형이며 POOL_KBN=0
- OBJ1800(가변패턴그룹): PGRPID, PGRPNAME, APPTYPEID(적용 유형: 대표상품·상품·담보 등), DISP_ORDER
- OBJ1810(패턴그룹별 유형): PGRPID, KIND(패턴 유형 ID)
- OBJ1110(유형별 표준항목) → OBJ1200(표준항목): 항목명(DISP_NAME)과 저장 컬럼(PHY_COLUMN1)

**EAV 해석 규칙**
- "약정기간" 같은 속성 값은 OBJ_DETAIL의 CHARnn 중 어느 컬럼인지 표준항목 정의로만 알 수 있다 → 항목 사전이 필요
- 같은 컬럼명이라도 유형(TYPEID)이나 패턴(KIND)마다 의미가 다르다 → 사전의 키는 (유형 또는 패턴, 항목명)
- 패턴 데이터는 같은 SID에 KIND=패턴 TYPEID인 행이 SEQ별로 여러 개 존재한다
- **버전 관리**: 새 버전이 생기면 이전 행의 END_DT가 닫히고 새 행이 새 시작일자로 생긴다. 최신 버전 행만 `END_DT = '99991231'`이다. 이 조건이 빠지면 같은 오브젝트가 버전 수만큼 중복 조회된다 (OBJ_MAIN, OBJ_INV, OBJ_DETAIL 모두 해당)

## 3. 모듈별 명세

### 3.1 메타데이터 (FR-02, FR-10)

- 구성: 테이블·컬럼 설명, 테이블별 유효조건과 기간 컬럼, 용어 사전(유형명→TYPEID, 관계명→INV_TYPE), 방언, 최대 행 수
- 인터페이스: `MetadataRepository.load()`. 구현체는 JSON 파일(기본), 이후 구글 시트
- 검증: 테이블·컬럼 식별자는 `^[A-Z][A-Z0-9_]*$`만 허용. 위반·파일 없음·형식 오류는 `MetadataError`
- 조회: 유형명(별칭, 대소문자 무시)으로 TYPEID 찾기. 없으면 오류
- **항목 사전** (FR-15): `{ 대상(유형명 또는 패턴명), 항목명, 별칭, 물리 컬럼, 값 유형(숫자/문자), 다중값 여부 }`. 물리 컬럼은 `^(CHAR|TEXT|DESC)\d{2,3}$`만 허용. 다중값 항목은 이번 PoC에서 미지원으로 표시
- **패턴 사전**: 패턴명 → 패턴 TYPEID(KIND 값), 소속 패턴그룹, 적용 유형
- 사전은 처음엔 손으로 작성하고, 서버 복구 후 OBJ1110·OBJ1200 조회 결과로 자동 생성한다
- **공통 메타데이터 + 사이트 프로필 분리** (FR-16)
  - 공통(`metadata/common.json`, 직접 관리): 테이블·컬럼 의미, 최신 버전 조건, 방언, 최대 행 수
  - 프로필(`metadata/sites/<사이트>.json`, 현장마다 다름): 유형명 → TYPEID, 패턴명 → 패턴 TYPEID, 항목명 → 물리 컬럼, **유형·항목별 별칭(현장마다 달라서 프로필에 둔다)**
  - 유형 항목 형태: `"기본상품": { "typeid": 901, "aliases": ["BaseProduct"] }`. 이름·별칭 조회는 대소문자를 구분하지 않는다
  - 구조(테이블·조인·템플릿)는 모든 현장이 같고 값만 다르므로, 현장이 바뀌면 프로필만 교체한다
  - 사용할 프로필은 설정값(`SITE`) 하나로 선택한다. 프로필에 없는 유형·항목은 `unsupported`로 거절하고 임의 값으로 대체하지 않는다
  - 프로필은 사람이 쓰지 않고 사이트 DB의 OBJ1000·OBJ1110·OBJ1200에서 **동기화 스크립트**로 생성한다 (서버 복구 후). 프로필 안에서 자동 생성 영역(유형·TYPEID·컬럼)과 사람이 적는 영역(별칭)을 구분하고, 재동기화 시 별칭은 덮어쓰지 않고 보존한다
  - 이번 PoC는 샘플 프로필(`sites/sample.json`) 하나로 개발한다
  - 동기화는 읽기 전용 계정으로 위 세 테이블만 조회한다
- 평가 케이스의 정답 SQL은 논리 이름을 쓰고, 평가 시 프로필로 TYPEID를 치환한다

### 3.2 의도(Intent) 모델 (FR-03~06)

| 필드 | 설명 |
|---|---|
| kind | `lookup`(단건) / `list`(목록) / `structure`(구성) / `attribute`(속성) / `pattern`(패턴 데이터) / `pattern_catalog`(패턴 구성) / `unsupported` |
| target_type | 대상 유형명 (예: 기본상품) |
| code | 오브젝트 코드. `^[A-Za-z0-9_.-]{1,32}$` |
| name_keyword | 이름 검색어. 최대 50자. `%` `_` 이스케이프 |
| direction | structure 전용: `children` / `parents` |
| related_type | structure 전용: 연결 대상 유형 (선택) |
| relation | `기본`(기본값) / `서비스뷰` |
| base_date | `YYYYMMDD`, 실제 존재하는 날짜. 미지정 시 적용기간 조건을 붙이지 않음 |
| attributes | 조회할 속성 항목명 목록 (예: ["약정기간"]). 항목 사전에 있는 이름만 허용 |
| pattern | 패턴명 (예: 패턴일반). 패턴 사전에 있는 이름만 허용 |
| pattern_group | 패턴그룹명 (패턴 구성 조회용) |
| reason | unsupported일 때 사유 |

종류별 필수값: lookup = target_type + (code 또는 name_keyword), list = target_type, structure = target_type + code + direction.

### 3.3 SQL 빌더 (FR-03~05, FR-07, FR-08, NFR-02, NFR-03, NFR-06)

공통 규칙
- 값은 모두 바인드 변수(`:name`)로 넣고, 복사용 문자열(rendered)은 이스케이프한 리터럴로 치환해 별도 제공
- 최신 버전 조건(`END_DT = '99991231'`)을 메타데이터에서 읽어 **모든 사용 테이블에** 자동 부착
- 질문에 기준일자가 있으면 `:base_dt BETWEEN VF_DT AND VT_DT`를 추가 (없으면 추가하지 않음). 과거 시점 버전 선택 규칙은 확인 필요 6.3-1
- 행 수 제한 없음 (2026-11-04 결정): 기준정보 관리 솔루션이라 결과를 잘라내지 않고 페이징도 하지 않는다. `FETCH FIRST`/`LIMIT`를 붙이지 않는다
- 방언: `postgresql`(기본), `oracle`. 한글 별칭은 큰따옴표(`"약정기간"`)로 감싼다. 테이블 별칭에 `AS`를 쓰지 않는다 (Oracle 호환)
- 식별자는 따옴표 없이 쓴다. PostgreSQL은 소문자로 접히므로 샘플 DB도 따옴표 없이 생성한다

템플릿

| ID | 질문 예 | 조립 결과 개요 |
|---|---|---|
| T1 lookup | "BP001 기본상품 정보 알려줘" | OBJ_MAIN을 TYPEID + BIZCODE(또는 OBJ_NAME LIKE)로 조회 |
| T2 list | "부가옵션 목록", "데이터가 들어간 기본상품" | OBJ_MAIN을 TYPEID(+이름 LIKE)로 조회, ORDER BY BIZCODE (DISP_ORDER는 화면 표시 순서라 제외) |
| T3 structure(children) | "BP001에 연결된 서비스" | OBJ_MAIN P → OBJ_INV(SID) → OBJ_MAIN C(SUBSID), INV_TYPE 조건, ORDER BY 결과 쪽 BIZCODE (DISP_SEQ는 화면 표시 순서일 가능성이 높아 제외, 구현 명세 1.4-3) |
| T4 structure(parents) | "AO001이 속한 기본상품" | T3의 방향 반대 |

| T5 attribute (FR-12) | "BP001 기본상품의 약정기간 알려줘" | OBJ_MAIN M → OBJ_DETAIL D (`D.SID = M.SID AND D.KIND = 1`), 항목 사전에서 찾은 물리 컬럼을 한글 별칭으로 SELECT. 두 테이블 모두 유효조건 부착 |
| T6 pattern (FR-13) | "A00001 대표상품의 패턴일반 보여줘" | OBJ_MAIN M → OBJ_DETAIL D (`D.KIND = :pattern_typeid`), 패턴 항목들을 한글 별칭으로 SELECT, ORDER BY D.SEQ |
| T7 pattern_catalog (FR-14) | "패턴그룹1에 어떤 패턴이 있어?" | OBJ1800 G → OBJ1810 R(PGRPID) → OBJ1000 T(`T.TYPEID = R.KIND`), 적용유형·패턴명 조회 |

- 속성·패턴의 물리 컬럼명은 **사용자 입력이 아니라 항목 사전에서만** 가져온다 (SELECT 절에 들어가므로 식별자 형식 검증 필수)
- T5·T6에서 OBJ_DETAIL에도 OBJ_MAIN과 동일하게 최신 버전 조건을 적용한다 (ERD상 동일 컬럼 보유)
- 다중값 항목과 값이 다른 오브젝트(OBJ_REL 경유)를 가리키는 항목은 `unsupported`

미지원 유형명·관계명·항목명은 `UnsupportedQuestionError`로 처리한다.

### 3.4 SQL 검증기 (NFR-01)

통과 조건: SELECT로 시작, 세미콜론·주석(`--`, `/* */`) 없음, 금지 키워드(INSERT, UPDATE, DELETE, DROP, ALTER, CREATE, TRUNCATE, MERGE, GRANT, EXEC, CALL, COPY, DO, SET) 없음, PostgreSQL 위험 함수(`pg_sleep`, `pg_read_file`, `lo_import`, `dblink` 등) 없음(문자열 리터럴 제외 후 검사), FROM·JOIN 뒤 테이블이 허용 목록(메타데이터 테이블) 안에 있음. 위반 시 `SqlValidationError`.

### 3.5 의도 추출기 (NFR-05, NFR-07)

- 인터페이스: `IntentExtractor.extract(question) -> Intent`
- 구현체: `OllamaIntentExtractor`(기본), `FakeIntentExtractor`(테스트·평가용), 필요 시 OpenAI
- Ollama 호출: `POST /api/chat`, `format: "json"`, `temperature: 0`, 스트리밍 끔
- 프롬프트: 메타데이터의 유형명·관계명 목록, 출력 JSON 스키마, 예시 3개 이상, "모르면 unsupported" 지시. 질문은 사용자 입력 구분자로 감싸 지시와 분리
- 오류: 서버 연결·HTTP 오류는 `LlmUnavailableError`, JSON·스키마 위반은 `IntentParseError`

### 3.6 서비스 (FR-01, FR-06, NFR-04)

`TextToSqlService.generate(question, request_id)`
1. 의도 추출 → 2. unsupported이면 즉시 거절 응답 → 3. 빌드 → 4. 검증 → 5. 결과 반환
- `IntentParseError`, `UnsupportedQuestionError`는 `status="unsupported"` 응답으로 변환하되 requestId와 함께 **로그에 기록**
- `LlmUnavailableError`, `SqlValidationError`는 변환하지 않고 상위로 전파

### 3.7 API

`POST /api/text-to-sql`

요청: `{ "question": "BP001 기본상품에 연결된 부가옵션 알려줘" }` (1~500자)

응답:
```json
{
  "requestId": "…",
  "status": "ok | unsupported",
  "sql": "SELECT … WHERE … :code …",
  "renderedSql": "SELECT … WHERE … 'BP001' …",
  "params": { "code": "BP001" },
  "intent": { "kind": "structure" },
  "message": null
}
```

| 상황 | HTTP |
|---|---|
| 정상, 지원하지 않는 질문 | 200 (status로 구분) |
| 질문이 비었거나 길이 초과 | 422 |
| LLM 서버 불가 | 502 |
| 검증기 차단·내부 오류 | 500 |

- 모든 응답에 `X-Request-ID` 헤더. 요청에 있으면 그대로 사용, 없으면 생성

### 3.8 평가 (FR-09)

- 케이스: `{id, question, gold_sql, intent}` 30개 내외. 실무 쿼리(기본상품·부가옵션·사급자재 등)로 채운다
- 판정: 생성 SQL과 정답 SQL을 샘플 DB에서 실행해 **결과 집합**이 같으면 통과 (SQL 문자열 비교 아님)
- 모드: 오라클 의도(빌더 회귀 검증) / 실제 LLM(Ollama) 두 가지
- 출력: 전체 정확도, 실패 케이스 목록, 지원 안 함으로 거절된 비율

## 4. 샘플 DB (개발·평가용)

**로컬 PostgreSQL**에 OBJ_MAIN, OBJ_INV, OBJ_DETAIL, OBJ1000, OBJ1800, OBJ1810, OBJ1110, OBJ1200 생성(필요한 컬럼만, CHAR01~CHAR05 정도). 생성 SQL을 실제 엔진에서 실행해 검증한다. 단위 테스트는 DB 없이 SQL 문자열만 검증하고, 실행 검증은 별도 통합 테스트로 분리한다. 유형 3개(기본상품·제공서비스·부가옵션, TYPEID는 샘플 값)와 아래 경계 케이스를 포함한다.
- 같은 오브젝트의 이전 버전 행(END_DT가 닫힌 행)과 최신 버전 행, 이전 버전 관계 행
- 적용기간이 지난 오브젝트 (기준일자 질문 검증용)
- 기본관계와 서비스뷰 관계가 모두 있는 오브젝트
- 이름이 같은 다른 유형의 오브젝트
