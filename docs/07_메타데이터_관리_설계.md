# 메타데이터 관리 설계 (구글 시트)

작성일: 2026-11-11 / 상태: **구현 완료 (2026-11-11, 미커밋)**. 실제 구글 시트 연결 확인 완료 (2026-11-12, demo 시트 → `[차이 없음]`) / 기준 문서: `01_요구사항정의서.md` FR-02·FR-10·FR-16, `05_구현명세서.md`
목적: 사이트 프로필(유형·별칭·항목·등록 항목명칭)을 **실제 현장에서 운영하는 방식**으로 관리한다. 현장 담당자는 구글 시트만 편집하고, 서비스는 검증된 스냅샷 파일만 읽는다.
표기: **[현행]** = 지금 코드에 있는 동작 / **[신규]** = 이 문서에서 새로 정하는 내용

## 1. 배경

### 1.1 지금 방식 [현행]

- 사이트 프로필은 사람이 직접 쓰는 JSON 파일 하나다: `src/text_to_sql/metadata/sites/<사이트>.json`
- 서비스가 시작할 때 `load_site_profile(path)`가 파일을 읽고 형식을 검사한다 (`repositories/metadata_repository.py`).
- 파일은 패키지 안에 있어서, 값을 하나 고치려면 text-to-sql을 다시 배포해야 한다.

### 1.2 문제

| 문제 | 실제 현장에서 생기는 일 |
|---|---|
| 현장 담당자가 JSON을 직접 고치기 어렵다 | 쉼표 하나 빠지면 서비스가 뜨지 않는다. 개발자만 고칠 수 있다 |
| 누가 무엇을 바꿨는지 보기 어렵다 | TYPEID나 컬럼이 바뀌면 같은 질문의 SQL 의미가 달라지는데 검토 절차가 없다 |
| 출처를 바꿀 교체 지점이 없다 | 모듈 주석에는 "인터페이스(Protocol)"라고 되어 있지만 실제로는 JSON을 읽는 함수만 있다 |
| 공지 권장 방식과 다르다 | PoC 공지가 "구글 스프레드시트에 정리 후 연동"을 추천했다 |

### 1.3 범위

| 구분 | 내용 |
|---|---|
| 포함 | 구글 시트 양식, 시트 → 스냅샷 JSON 동기화 도구, 검증·차이 보고, 출처 교체 구조, 운영 절차 |
| 포함 | 대상 테이블은 지금과 같이 OBJ_MAIN, OBJ_INV, OBJ_DETAIL 3개 |
| 제외 | 현장 DB 메타 테이블(OBJ1000, OBJ1110, OBJ1200)에서 유형·항목 자동 수집 (11장 로드맵) |
| 제외 | 공통 메타데이터(`common.json`: 테이블·버전 조건). 현장마다 바뀌지 않으므로 파일 그대로 둔다 |
| 제외 | 챗봇 관리자 화면에서 메타데이터 편집 |

## 2. 전체 구조 [신규]

```
 ┌──────────────────────┐   ① 편집 (현장 담당자)
 │ 구글 시트 (사이트당 1개) │   유형 · 별칭 · 항목 · 등록항목 · 테이블별칭 · 설정 탭
 └──────────┬───────────┘
            │ ② 동기화 도구가 읽기 (서비스 계정, 읽기 전용 권한)
            ▼
 ┌──────────────────────┐   ③ 검증: 형식 · 중복 · 참조 오류를 탭·행 번호와 함께 전부 보고
 │ 동기화 도구 (CLI)       │   ④ 차이 보고: 지금 스냅샷과 비교 (추가 · 삭제 · 변경, 위험 변경 표시)
 └──────────┬───────────┘
            │ ⑤ --apply 일 때만, 검증을 통과한 경우에만 저장
            ▼
 ┌──────────────────────┐   버전 정보(_meta) 포함. git으로 이력 관리
 │ 스냅샷 sites/<사이트>.json │
 └──────────┬───────────┘
            │ ⑥ 서비스 시작 시 읽기 (지금과 같은 로더)
            ▼
 ┌──────────────────────┐
 │ TextToSqlService      │   로그에 프로필 버전을 남긴다 (requestId + 메타데이터 버전으로 재현)
 └──────────────────────┘
```

### 2.1 설계 원칙

1. **서비스는 시트를 직접 읽지 않는다.** 요청마다 또는 시작할 때마다 시트를 읽으면, 누군가 시트를 잘못 고친 순간 서비스가 바로 망가진다. 구글 API 장애나 사내망 차단에도 영향을 받는다. 서비스는 검증을 통과한 스냅샷만 읽는다.
2. **검증에 실패하면 스냅샷을 바꾸지 않는다.** 오류가 하나라도 있으면 저장하지 않고 오류 목록만 출력한다.
3. **기본은 미리보기(dry-run)다.** 실제 저장은 `--apply`를 붙였을 때만 한다. 사람이 차이 보고를 보고 판단한다.
4. **오류는 첫 번째만이 아니라 전부 보여 준다.** 현장 담당자가 한 번에 고칠 수 있도록 "탭 이름, 행 번호, 무엇이 잘못됐는지"를 모두 출력한다.
5. **스냅샷 형식은 지금 JSON과 같다.** 기존 로더·빌더·추출기는 바꾸지 않는다. `_meta`만 추가하는데, 지금 로더는 모르는 키를 무시하므로 하위 호환이 된다.
6. **이력은 git이 맡는다.** 스냅샷 파일을 커밋하면 "언제, 무엇이, 왜" 바뀌었는지가 남는다. 시트 자체의 버전 기록은 보조 수단이다.

## 3. 시트 양식 [신규]

### 3.1 공통 규칙

- **스프레드시트 1개 = 사이트 1개.** 현장마다 권한과 담당자가 다르기 때문이다. 새 현장은 템플릿 시트를 복사해서 시작한다.
- 각 탭의 **1행은 헤더**다. 헤더 이름과 순서는 바꾸지 않는다. 동기화 도구는 헤더 이름으로 열을 찾는다. 열 순서가 바뀌어도 동작하지만, 헤더 이름이 다르면 오류를 낸다.
- **2행부터 데이터**다. 완전히 빈 행은 건너뛴다.
- 모든 칸은 **앞뒤 공백을 지우고** 읽는다.
- `사용` 열: `Y`면 반영하고 `N`이면 제외한다. 빈 칸은 `Y`로 본다. 삭제하지 않고 잠시 빼 둘 때 쓴다.
- `설명` 열: 사람을 위한 메모다. 스냅샷에는 넣지 않는다.
- 숫자 칸(TYPEID)은 시트 서식을 **일반 텍스트**로 둔다. 숫자 서식이면 `1,100`이나 `1100.0`처럼 읽힐 수 있다.

### 3.2 `설정` 탭

| 키 | 값 (예) | 설명 |
|---|---|---|
| site | demo | 사이트 이름. 스냅샷 파일 이름이 된다 (`sites/demo.json`). 영문·숫자·`_`·`-`만 쓴다 |
| 담당자 | (이름) | 메모. 스냅샷 `_meta.owner`에 들어간다 |

헤더는 `키 | 값`이다. 동기화 도구에 넘긴 `--site`와 이 탭의 `site`가 다르면 오류를 낸다 (다른 현장 시트를 잘못 연결하는 사고를 막는다).

### 3.3 `유형` 탭 → 스냅샷 `types`

| 유형명 | TYPEID | 사용 | 설명 |
|---|---|---|---|
| 보험상품 | 1100 | Y | 보험 업권 최상위 상품 |
| 주계약 | 1110 | Y | |
| 특약 | 1120 | Y | |

- 유형명: 한글·영문·숫자·`_`, 1~30자. 유형명은 계층 조회 SQL의 열 이름(`"보험상품"`)으로도 쓰이기 때문이다.
- TYPEID: 양의 정수.
- 유형명 중복 금지, TYPEID 중복 금지.

### 3.4 `별칭` 탭 → 스냅샷 `aliases`

| 별칭 | 유형명 | 사용 | 설명 |
|---|---|---|---|
| 라이더 | 특약 | Y | 현장에서 특약을 라이더라고 부름 |
| 선택특약 | 특약 | Y | |
| 보험 | 보험상품 | Y | |

- 유형명은 `유형` 탭에서 **사용=Y인 유형**이어야 한다.
- 별칭 중복 금지. 같은 별칭이 두 유형을 가리키면 오류다.
- 별칭이 다른 유형의 정식 이름과 같으면 오류다 (예: 별칭 `특약 → 보장`).
- **정식 이름을 자기 자신에게 연결하는 줄은 적지 않는다.** 지금 JSON은 `"특약": "특약"`처럼 정식 이름도 aliases에 넣어 두는데, 동기화 도구가 자동으로 채운다. 담당자는 "다르게 부르는 이름"만 적으면 된다.

### 3.5 `항목` 탭 → 스냅샷 `items`

| 유형명 | 항목명 | 물리컬럼 | 다중값 | 형식 | 사용 | 설명 |
|---|---|---|---|---|---|---|
| 보험상품 | 보험기간 | CHAR01 | N | 문자 | Y | |
| 보험상품 | 가입최저나이 | CHAR03 | N | 숫자 | Y | 값 조건 검색에서 숫자로 비교 |
| 보험상품 | 판매채널 | CHAR05 | Y | 문자 | Y | 다중값이라 지금은 조회 거절 |
| 보장 | 지급사유 | TEXT01 | N | 문자 | Y | |

- `형식` 열은 선택이다 (2026-11-12 추가, 설계 08). 없거나 빈 칸이면 문자. 값은 `숫자`/`number`, `문자`/`text`.

- 유형명: `유형` 탭에서 사용=Y인 유형.
- 항목명: 한글·영문·숫자·`_`, 1~30자.
- 물리컬럼: `CHAR`·`TEXT`·`DESC` 뒤에 숫자 2~3자리 (예: `CHAR01`, `TEXT01`). 소문자로 적어도 대문자로 바꿔 읽는다.
- 다중값: `Y`/`N`. 빈 칸은 `N`.
- 같은 유형 안에서 항목명 중복 금지, 같은 유형 안에서 물리컬럼 중복 금지 (두 항목이 한 컬럼을 가리키면 둘 중 하나는 틀린 값이다).

### 3.6 `등록항목` 탭 → 스냅샷 `registered_items`

| 항목명칭 | 사용 | 설명 |
|---|---|---|
| 상품코드 | Y | 솔루션 항목관리에 등록된 룰 변수 |
| 수수료코드 | Y | |

- 항목명칭: 한글·영문·숫자·`_`, 1~30자. 중복 금지.
- 시트에 적힌 순서를 그대로 유지한다 (첫 항목이 프롬프트 예시에 쓰인다).

### 3.7 `테이블별칭` 탭 → 스냅샷 `table_aliases`

| 역할 | 별칭 | 설명 |
|---|---|---|
| main | M | 단건·목록·속성 조회의 OBJ_MAIN |
| parent | P | 구조 조회의 상위 OBJ_MAIN |
| inv | I | OBJ_INV |
| child | C | 구조 조회의 하위 OBJ_MAIN |
| detail | D | OBJ_DETAIL |

- 탭이 없거나 비어 있으면 기본값(M/P/I/C/D)을 쓴다. 적은 역할만 덮어쓴다 [현행 로더와 같음].
- 역할은 위 5개만 쓸 수 있다. 별칭은 영문 대문자로 시작하고 대문자·숫자·`_`만 쓴다. 별칭끼리 중복 금지.

## 4. 검증 규칙 [신규]

동기화 도구는 시트를 다 읽은 뒤 아래 규칙을 **모두** 검사하고, 오류를 한꺼번에 출력한다.

| 코드 | 탭 | 규칙 |
|---|---|---|
| MV-01 | 전체 | 필수 탭(`설정`, `유형`)이 있고, 각 탭 헤더에 필수 열이 있다 |
| MV-02 | 설정 | `site`가 있고, 형식이 맞고, `--site`와 같다 |
| MV-03 | 유형 | 유형명 형식, TYPEID 양의 정수, 유형명·TYPEID 중복 없음, 사용=Y 유형이 1개 이상 |
| MV-04 | 별칭 | 가리키는 유형이 있음, 별칭 중복 없음, 다른 유형의 정식 이름과 겹치지 않음 |
| MV-05 | 항목 | 유형 있음, 항목명·물리컬럼 형식, 유형 안에서 항목명·물리컬럼 중복 없음, 다중값 Y/N |
| MV-06 | 등록항목 | 형식, 중복 없음 |
| MV-07 | 테이블별칭 | 역할 5개 중 하나, 별칭 형식, 중복 없음 |
| MV-08 | 전체 | `사용` 칸은 Y/N/빈 칸만 |
| MV-09 | 전체 | 최종 결과를 지금 로더(`load_site_profile`과 같은 검사)에 한 번 더 통과시킨다. 시트 규칙과 로더 규칙이 어긋나도 잘못된 스냅샷이 저장되지 않는다 |

오류 출력 예:

```
[검증 실패] 3건 — 스냅샷을 저장하지 않았습니다
  MV-03 유형 5행: TYPEID '11O0'은 정수가 아닙니다
  MV-04 별칭 9행: '라이더'가 두 번 나옵니다 (7행과 중복)
  MV-05 항목 14행: 물리컬럼 'CHAR1'은 형식이 맞지 않습니다 (예: CHAR01)
```

`사용=N`인 유형을 가리키는 별칭·항목은 오류가 아니라 **경고**로 출력하고 함께 제외한다 (유형을 잠시 빼 둘 때 관련 줄까지 일일이 N으로 바꾸지 않아도 되게).

유형 행 자체에 오류가 있으면(예: TYPEID 오타), 그 유형을 가리키는 별칭·항목 줄에는 "없는 유형" 오류를 **겹쳐 내지 않는다**. TYPEID 하나가 틀렸는데 오류가 수십 줄 나오면 진짜 원인을 찾기 어렵기 때문이다 (구현 중 실제로 1건이 7건으로 불어나는 것을 보고 추가함).

필수 열이 아닌 `사용`·`다중값`·`설명` 열은 헤더에 없어도 된다. 없으면 사용=Y, 다중값=N으로 본다.

## 5. 차이 보고 [신규]

검증을 통과하면 지금 스냅샷과 비교해 차이를 출력한다. 스냅샷이 아직 없으면 "새로 만듦"으로 표시한다.

| 구분 | 출력 예 | 위험 |
|---|---|---|
| 유형 추가·삭제 | `+ 유형 연금상품: 1150` | 삭제는 위험 |
| **TYPEID 변경** | `~ 유형 특약: 1120 → 1125 [위험]` | 위험. 같은 질문의 SQL이 다른 데이터를 조회한다 |
| 별칭 추가·삭제·대상 변경 | `~ 별칭 라이더: 특약 → 보장 [위험]` | 대상 변경만 위험 |
| 항목 추가·삭제 | `+ 항목 보험상품.갱신주기: CHAR06` | 삭제는 위험 |
| **물리컬럼 변경** | `~ 항목 보험상품.보험기간: 물리컬럼 CHAR01 → CHAR07 [위험]` | 위험 |
| 다중값 변경 | `~ 항목 펀드.투자지역: 다중값 Y → N` | |
| 등록항목 추가·삭제 | `- 등록항목 요율코드: 삭제` | |
| 테이블별칭 변경 | `~ 테이블별칭 main: M → OMA [위험]` | 위험. 출력 SQL 모양이 바뀐다 |

출력 마지막에 `추가 N · 삭제 N · 변경 N (위험 N)`을 요약한다. 위험 변경이 있으면 `--apply` 때 한 번 더 확인하도록 `--yes` 없이는 저장하지 않는다.

- 기존 스냅샷이 없으면 전부 "추가"로 보고하고 위험으로 보지 않는다. 테이블별칭은 기본값(M/P/I/C/D)과 비교하므로 기본값과 다른 것만 "변경"으로 나온다.
- 차이가 없으면 `--apply`여도 파일을 다시 쓰지 않는다 (버전만 바뀌는 커밋이 생기지 않게).
- 위험 표시는 `⚠` 대신 `[위험]` 글자로 쓴다. 윈도우에서 출력을 파일·파이프로 넘기면 cp949로 인코딩되는데, `⚠`는 cp949에 없어서 출력이 실패한다.

## 6. 스냅샷 형식 [신규]

지금 JSON에 `_meta`만 더한다.

```json
{
  "_meta": {
    "version": "2026-11-12T10:30:00+09:00",
    "source": "google_sheet",
    "sheet_id": "1AbC...xyz",
    "owner": "(설정 탭 담당자)",
    "synced_by": "sync_site_profile 0.1.0"
  },
  "site": "demo",
  "types": { "보험상품": 1100 },
  "aliases": { "보험상품": "보험상품", "보험": "보험상품" },
  "table_aliases": { "main": "M", "parent": "P", "inv": "I", "child": "C", "detail": "D" },
  "items": { "보험상품": { "보험기간": { "column": "CHAR01" } } },
  "registered_items": ["상품코드"]
}
```

- 키 순서와 들여쓰기를 고정한다 (`ensure_ascii=False`, 2칸 들여쓰기, 유형은 시트 순서). 그래야 git diff가 실제 변경만 보여 준다.
- `version`은 동기화 시각이다. 서비스는 시작할 때 `프로필 로드 site=demo version=...`을 로그로 남긴다. 질문 로그의 requestId와 함께 보면 "그 질문을 어느 메타데이터로 처리했는지" 재현할 수 있다.
- `_meta`가 없는 옛 파일(지금의 demo.json, sample.json)도 그대로 읽힌다.

### 6.1 스냅샷 위치

| 환경 | 위치 | 이유 |
|---|---|---|
| 개발·테스트 | 패키지 안 `metadata/sites/` [현행] | 테스트 고정값(sample)과 시연값(demo)을 코드와 함께 관리 |
| 현장 운영 | 패키지 밖 폴더, `TTS_METADATA_DIR`로 지정 [현행 설정 활용] | 메타데이터만 바꿀 때 text-to-sql을 다시 배포하지 않는다 |

현장 운영 폴더에는 `common.json`도 함께 둔다 (`TTS_METADATA_DIR`은 두 파일을 같은 폴더에서 찾는다).

## 7. 동기화 도구 (CLI) [신규]

### 7.1 사용법

```bash
# 미리보기: 시트를 읽어 검증하고 차이만 출력 (아무것도 저장하지 않음)
python -m text_to_sql.sync --site demo --sheet-id <스프레드시트 ID>

# 저장: 검증을 통과하면 스냅샷을 쓴다. 위험 변경이 있으면 --yes가 필요
python -m text_to_sql.sync --site demo --sheet-id <ID> --apply [--yes]

# 처음 한 번: 지금 JSON을 시트 양식(CSV 탭별 파일)으로 내보내 템플릿을 채운다
python -m text_to_sql.sync --site demo --export-csv out/
```

| 옵션 | 기본값 | 설명 |
|---|---|---|
| `--site` | (필수) | 사이트 이름. 설정 탭의 site와 같아야 한다 |
| `--sheet-id` | 환경변수 `TTS_SHEET_ID` | 스프레드시트 URL의 `/d/`와 `/edit` 사이 문자열 |
| `--credentials` | 환경변수 `TTS_GOOGLE_CREDENTIALS` | 서비스 계정 키 JSON 파일 경로 |
| `--out-dir` | `TTS_METADATA_DIR` 또는 패키지 `metadata/` | 스냅샷을 쓸 폴더 (`<out-dir>/sites/<site>.json`) |
| `--apply` | 꺼짐 | 저장한다 |
| `--yes` | 꺼짐 | 위험 변경이 있어도 저장한다 |
| `--export-csv` | - | 지금 스냅샷을 탭별 CSV로 내보낸다 (시트 첫 작성·이관용) |
| `--csv-dir` | - | 시트 대신 탭별 CSV 폴더(`<탭 이름>.csv`)에서 읽는다. 시트 없이 시험하거나 사내망에서 구글에 못 붙을 때 |

`--csv-dir`를 주면 `--sheet-id`·`--credentials`는 쓰지 않는다. 스냅샷 `_meta.source`는 `csv`, 시트에서 읽으면 `google_sheet`가 된다.

### 7.2 종료 코드

| 코드 | 의미 |
|---|---|
| 0 | 성공 (미리보기 완료, 또는 저장 완료, 또는 차이 없음) |
| 1 | 검증 실패 (스냅샷 그대로) |
| 2 | 시트 접근 실패 (인증·권한·네트워크·시트 ID 오류). 원인 예외를 함께 출력 |
| 3 | 위험 변경이 있는데 `--yes` 없이 `--apply` |

종료 코드를 나눠 두면 나중에 CI나 배치에서 자동으로 돌릴 때 분기할 수 있다.

## 8. 인증과 보안 [신규]

- **방식**: 구글 클라우드 **서비스 계정**. 사람 계정 OAuth는 쓰지 않는다 (서버·배치에서 사람 로그인이 필요 없도록).
- **권한**: 스프레드시트를 서비스 계정 이메일에 **뷰어**로만 공유한다. 코드도 읽기 전용 범위(`gspread.auth.READONLY_SCOPES`)로 인증한다. 동기화 도구는 시트에 쓰지 않는다.
- **키 파일**: `TTS_GOOGLE_CREDENTIALS`로 경로만 넘긴다. 저장소에는 절대 넣지 않는다 (`.gitignore`에 `*credentials*.json` 추가).
- **시트에 들어가는 정보**: 유형명·TYPEID·컬럼 매핑·별칭뿐이다. 고객·상품 데이터 값은 없다. 그래도 현장 구성 정보이므로 링크 공개("링크가 있는 모든 사용자")는 쓰지 않는다.
- **쓰지 않는 방법**: "웹에 게시"한 CSV 주소로 읽는 방식은 라이브러리 없이 되지만, 주소만 알면 누구나 볼 수 있어서 쓰지 않는다.
- **사내망 차단 대비**: 현장 서버에서 구글에 접속할 수 없으면 담당자 PC에서 동기화하고, 스냅샷 파일만 현장 서버에 반영한다. 서비스가 시트를 직접 읽지 않으므로(원칙 1) 이 방식으로도 운영할 수 있다.

## 9. 코드 구조 [신규]

### 9.1 파일

| 파일 | 역할 | 비고 |
|---|---|---|
| `repositories/metadata_repository.py` | `load_site_profile(path)`를 **파일 읽기**와 **검증·변환**(`parse_site_profile(data, origin)`)으로 나눈다 | 동작은 그대로. 기존 테스트가 그대로 통과해야 한다 |
| `repositories/profile_source.py` | `ProfileSource` Protocol, `Tabs` 타입, `CsvFolderSource` | 출처 교체 지점 |
| `repositories/sheet_source.py` | `GoogleSheetSource`, `open_google_sheet` | gspread를 import하는 유일한 파일 |
| `sync/sheet_rows.py` | 행 목록 → `SiteProfile` 변환 + MV-01~09 검증 (순수 함수) | 네트워크 없이 테스트 |
| `sync/diff.py` | 두 `SiteProfile`의 차이와 위험 판정 (순수 함수) | |
| `sync/snapshot.py` | 스냅샷 JSON 만들기·쓰기(임시 파일 후 바꿔치기), 탭별 CSV 내보내기 | |
| `sync/cli.py`, `sync/__main__.py` | CLI: 인자 처리, 출력, 종료 코드 | `main(argv, env, sheet_factory, now)`로 테스트 |
| `errors.py` | `ProfileSourceError` 추가 | 시트·CSV 접근 실패 |

### 9.2 인터페이스

```python
# [스프링] 출처별 구현체를 갈아 끼우는 인터페이스 (Repository 인터페이스와 같은 역할)
class ProfileSource(Protocol):
    def read_tabs(self) -> dict[str, list[list[str]]]:
        """탭 이름 → 행 목록(1행은 헤더). 값은 모두 문자열."""
        ...

class GoogleSheetSource:
    def __init__(self, client: SheetClient, sheet_id: str) -> None: ...
    # spreadsheet.worksheets()로 탭을 돌며 worksheet.get_all_values()로 읽는다
    # SheetClient는 gspread.Client 중 open_by_key만 적은 Protocol (테스트에서 가짜를 넘긴다)

class CsvFolderSource:          # 시트 없이 시험·이관 확인용 (<탭 이름>.csv)
    def __init__(self, folder: Path) -> None: ...

def rows_to_profile(tabs: Tabs, site: str) -> ProfileBuildResult: ...
#   ProfileBuildResult(profile: SiteProfile | None, owner, errors: list[RowIssue], warnings)

def diff_profiles(old: SiteProfile | None, new: SiteProfile) -> list[Change]: ...
#   Change(kind: "add" | "remove" | "change", target: str, detail: str, risky: bool)
```

차이 비교는 원본 JSON이 아니라 로더가 읽은 `SiteProfile`끼리 한다. 그래서 손으로 쓴 옛 파일(`table_aliases`·`_meta` 없음)과 동기화 도구가 쓴 스냅샷도 내용이 같으면 "차이 없음"으로 나온다.

- 시트를 읽을 때 `get_all_records()`가 아니라 `get_all_values()`를 쓴다. `get_all_records()`는 숫자처럼 보이는 값을 숫자로 바꾸고 행 번호를 잃는다. 우리는 문자열 그대로 받아 직접 검사하고, 오류에 행 번호를 붙여야 한다.
- `GoogleSheetSource`는 `gspread.Client`를 생성자로 받는다 (의존성 주입). 테스트에서는 가짜 클라이언트나 `CsvFolderSource`를 쓰므로 구글 접속이 필요 없다.

### 9.3 의존성

- 새 라이브러리: `gspread`(6.x, 내부적으로 `google-auth` 사용).
- **선택 설치(extra)로 둔다**: `pip install "text-to-sql[sheets]"`. 챗봇은 스냅샷만 읽으므로 gspread를 설치할 필요가 없다. gspread는 동기화 도구를 돌리는 곳에만 설치한다.

```toml
[project.optional-dependencies]
sheets = ["gspread>=6.1"]
```

- `sheet_source.py`만 gspread를 import한다. 다른 모듈은 gspread 없이도 import되어야 한다 (mypy·테스트 포함).

### 9.4 서비스 쪽 변경

- `factory.create_service()`가 프로필을 읽은 뒤 `logger.info("프로필 로드 site=%s version=%s", ...)`를 남긴다. `_meta`가 없으면 `version=unknown`.
- 그 밖에 빌더·추출기·검증기·서비스는 바꾸지 않는다.

## 10. 운영 절차 [신규]

### 10.1 새 현장 시작

| 순서 | 누가 | 할 일 |
|---|---|---|
| 1 | 개발자 | 템플릿 시트를 복사해 현장용 시트를 만든다 (`--export-csv`로 demo를 내보내 템플릿을 만들어 둔다) |
| 2 | 개발자 | 시트를 서비스 계정 이메일에 뷰어로 공유한다 |
| 3 | 현장 담당자 | `설정` 탭의 site, `유형` 탭(유형명·TYPEID), `항목` 탭(항목명·물리컬럼)을 채운다. 값은 현장 솔루션의 유형·항목 관리 화면에서 확인한다 |
| 4 | 현장 담당자 | 현장에서 부르는 다른 이름을 `별칭` 탭에, 룰 변수로 쓰는 항목명칭을 `등록항목` 탭에 적는다 |
| 5 | 개발자 | 미리보기 실행 → 오류가 있으면 담당자에게 오류 목록(탭·행 번호)을 전달한다 |
| 6 | 개발자 | 오류가 없으면 `--apply` → 스냅샷 커밋 → 서비스 재시작 |
| 7 | 함께 | 시연 질문 몇 개로 SQL을 확인한다 |

### 10.2 별칭·항목 추가 (평소 운영)

챗봇 SQL 모드의 미답변(거절) 처리와 연결된다.

```
사용자 질문 "선택특약 목록" → 거절 (별칭 없음)
  → 관리자 화면 미답변 목록에 "없는 유형·별칭" 사유로 표시
  → 현장 담당자가 시트 별칭 탭에 "선택특약 | 특약" 추가
  → 동기화 미리보기: "+ 별칭 선택특약 → 특약" 확인 → --apply → 서비스 재시작
  → 같은 질문이 SQL로 답해진다 (코드 수정 없음)
```

### 10.3 반영 방식

- 이번 설계는 **서비스 재시작으로 반영**한다. 프로필은 시작할 때 한 번 읽는다 [현행].
- 재시작 없이 반영하는 기능(관리자 API로 다시 읽기)은 필요해지면 추가한다. 다시 읽는 중에 들어온 요청 처리, 프롬프트 캐시 재예열(약 100초)까지 고려해야 해서 이번 범위에서 뺐다.
